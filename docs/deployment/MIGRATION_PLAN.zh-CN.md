# AWS + Docker 迁移计划

目标是在云端接续同一条研究谱系，保持原模型、资源、预算、数据边界和重试规则，以及原 Docker 安全参数和 8 秒身份检查。

本计划是公开工程说明。具体账户、路径、数据、状态及接管凭据在受控环境中填写；合成测试通过不代表完整迁移已完成。

## 迁移范围

| 类别 | 内容 | 验收条件 |
| --- | --- | --- |
| 代码与版本 | 最新可运行 Source、真实 launcher/runner/guest、全部导入模块、配置和包资源 | 明确文件白名单、大小、哈希和版本证据，重新通过原 Source 准入 |
| Linux 环境 | 固定 Python、依赖锁和构建输入、Docker digest、host profile、必要系统库 | 重建并验证 Linux 环境；真实原 guest/runner 可用，全部身份检查保留 |
| 必要输入 | 已确认可迁移的数据快照、规则、选定产物和索引 | 逐项确认传输范围、只读属性、完整性、容量和原引用 |
| 续跑状态 | 同一权威账本、当前研究记忆、完成位置和所引用的收尾证据闭包 | 原任务完整收尾后导出一致性恢复包，目标端验证谱系与全部原门禁 |
| 运维配置 | 非秘密启动参数、日志和状态落点、监测、预算控制、停止保护及回滚说明 | 客户端断线后可回连并取得真实退出码；停机等待工作、费用和状态收尾 |

凭据通过原受控方式单独提供最小必要权限。活跃锁、PID、socket、旧 lease、本机登录缓存和 Mac 虚拟环境不作为迁移包；云端按原协议重新建立运行实例，保持唯一逻辑 owner 和唯一权威账本。

受保护输入、原始模型响应、私有推理及私有 Git 历史不进入普通工程包。需要这些内容的能力须由原 owner 按既有规则单独解决供应；不能通过删掉原校验来完成迁移。

## 执行顺序

1. **盘点并冻结版本。** 确定当前 Source、普通工程依赖闭包、规范路径、必要输入和原 owner 的收尾/接管入口，填写[清单模板](migration-inventory.template.json)。未核验字段保持空值。
2. **先部署代码与环境。** 目标端研究入口保持禁用，核验包完整性、Linux native 库、导入根、权限及 host profile。旧源码快照不能代替当前准入。
3. **验证完整原实现。** 使用确认无付费派发和研究状态副作用的检查入口，验证真实 runner/guest、身份/超时/清理、持久化和断线退出码。独立合成示例不能认证原实现。
4. **收尾后交接状态。** 冻结本地派发，等待真实退出、费用结算、未知请求处理、清理和 memory 终态完成。由原 owner 导出一致性包，目标端仍禁用派发，校验后完成唯一接管，再恢复运行。
5. **有限恢复并验收。** 依照原协议运行一个有限工作单位，验证退出、清理、费用、账本、memory 和最终收尾。通过后才记录迁移完成，保留本地恢复备份。

## Memory 的迁移要求

执行链必须同时保留 memory helper、prepare/current-input guard、runner 生命周期，以及实际角色输入核验依赖。

恢复链包含当前权威 memory、不可变 predecessor snapshot/update、原 terminal、匹配的 closure/private-seal metadata、Source/runtime 绑定和原 chronology/failure 证据。具体有限闭包由原 owner 导出，不能只挑最后一次成功记录。

原校验依赖规范绝对路径、原字节和哈希。若改变布局，先验证原协议支持的迁移接缝并取得新准入；不全局改写历史 JSON 或使用符号链接代替规范路径。公开的精选 memory view 缺少恢复闭包，不能当恢复包。

Memory 的 check-then-rename 依赖唯一 writer，不能提供跨主机原子 CAS。本地冻结和目标端接管必须有实际证据。新任务重新执行原 prepare 和准入，不直接复用本地运行许可。

搜索起点回到根节点时，保留既有 memory、版本池、账本和历史；搜索起点变化不清零状态。仍未获准的研究入口在云端继续受原路由约束。

## 必须验证的失败路径

- 缺失或过期 memory、feedback/前驱不一致、遗留 active、记账失败或更晚 terminal 会阻止派发。
- 未结算费用、未完成清理或封口不符不能由 memory 更新代替。
- 成功、拒绝和失败自动写回；写回错误保留原 terminal，不提供付费重试权。
- 冻结预测窗口只读 Supervisor memory 作 bookkeeping，预测输入保持不变。
- 未知请求不重发；停机不依据 CPU 空闲或结果文件出现。

Bootstrap 的固定停机 timer 只适合有限合成任务。正式研究运行前，先安装并验证按原收尾条件停机的机制，再切换停止策略；新保护未就绪时保持研究入口禁用。

## 回滚

目标端尚未派发或改动状态时，先确认其入口禁用、进程退出且接管权释放，再由原 owner 恢复本地运行。

目标端已派发或写状态后，先冻结目标端并处理未知请求、费用和状态，导出最新一致性包，再进行反向接管。不能直接重启旧本地快照，或产生第二份权威账本。
