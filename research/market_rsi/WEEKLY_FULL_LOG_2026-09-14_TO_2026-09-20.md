## Important interpretation boundaries

### MSE values from different experiments are not directly comparable

The memory pilot, memory-policy v4 and NFL event-prediction experiments use different cohorts, row definitions and targets. Their MSE scales cannot be compared as if they were one continuous leaderboard.

### The memory routes mean different context policies

- **Fresh:** the Controller does not receive the accumulated full experiment archive as memory.
- **Archive:** the Controller receives the retained prior experiment archive and can reuse earlier findings.
- **Compact:** the Controller receives a compressed representation of prior experience.
- **Baseline:** a fixed ordinary predictor defined before the comparison; in the v4 Final table this is the fixed one-feature Ridge candidate, not a random predictor.

### Opened Train is not independent confirmation

Repeated Train-only improvements are useful for debugging and selecting a direction. They do not establish unseen-date generalization. The same is true of post-hoc analysis on already opened Final sessions.

- at least 20 untouched sessions;
- per-session paired deltas;
- positive-session and positive-market fractions;
- concentration of gains;
- calibration;
- no post-score reward changes.

### Effect

The scientific claim became more accurate, but this did not create new independent evidence.

## 2026-09-15 — Full memory experiment, repeated failure repair, and Final result

### What was done

#### v4

- The terminal-submission protocol was redesigned.
- A fresh data split was frozen.
- Eight full rounds completed across Fresh, Archive and Compact.
- A one-time 20-session Final completed with 0 missing, 0 duplicate and 0 pending sessions.

### Where v2 got stuck and why

The v2 Fresh route fit a 9-feature Ridge candidate on 4,426,632 rows under the original resource limit. It then attempted the mandatory complete refit on 6,105,040 rows. Peak memory rose to approximately 2,317,184 KiB, exceeding the original 2 GiB boundary.

This was not a bad score, provider failure or budget exhaustion. The harness had used the same insufficient resource ceiling for a smaller candidate fit and a much larger final refit.

### v2 fix

- Candidate fit: 6 GiB / 480 seconds.
- Full refit: 8 GiB / 600 seconds.
- Cumulative Train semantic-observation limit: 10,000,000.
- The exact 6,105,040-row refit was rerun as a score-free positive canary and completed.
- v2 was not resumed because it had already consumed two rolling Dev scores.
- v3 used a fresh ID and new unseen Dev/Final membership.

### Where v3 got stuck and why

During Round 3, Compact used 25 paid turns and 25 real tool calls. The final provider turn ended with `length`; only 234 output tokens remained, and the Controller never called `submit_candidate`.

The provider, tools and candidate fitting had worked. This was a real terminal-protocol failure under the frozen resource policy, not a transient transport problem. It could not be retried in place.

### v3 fix

The v4 protocol reserved:

- 16,384 output tokens for terminal submission;
- four tool calls for terminal work;
- a mode where only `submit_candidate` remains visible after the terminal threshold.

The runner was still forbidden from guessing a candidate from prose or sampling another answer.

A live terminal canary passed with one provider call and a cost of `$0.00223803`. It used synthetic input and did not contain market data or a score.

### Other system problems found in preparation

1. **Wrong contract path:** the first v4 admission attempt passed an old admission report instead of the frozen contract. It failed before labels, fit, provider calls or scores. The failure ID was preserved; a new ID was used after repair.
2. **Missing stderr evidence:** the first contract failure preserved only a `ValueError`. The transfer layer was changed to retain bounded stderr, remote exit code, byte count and hashes.
3. **iCloud placeholders:** 2,409 Tinker/Transformers/Hugging Face runtime files were present as cloud placeholders. The runner had not yet called the provider, but waited while files hydrated.
4. **Short broker lock conflict:** a complete synthetic canary failed when `interpret_result` briefly contended for the local broker lock. The local tool layer was changed to wait for up to five seconds; persistent contention still fails closed.

## 2026-09-17 — E2B failure diagnosis and pivot to local Docker B

The intended early architecture used two E2B sandboxes:

- A: Controller-side process;

### Second live E2B failure

- public URL through proxy: completed;
- public URL direct: completed;
- peer URL through environment proxy: started but did not complete;
- B→A: not started;
- complete guest report: absent.

Both exact sandboxes were later confirmed killed, and no Market RSI E2B sandbox remained. The ledger carried a conservative `$0.20` uncertain upper bound. This was not treated as a provider invoice.

### What the logs showed

The central architecture error was not only latency. The system was testing symmetric A↔B communication even though the intended security relationship was asymmetric:

- A/Controller must assign work and see allowed B results;
- B/Researcher must not directly access A;
- the trusted broker should carry tasks and observations;
- frequent direct sandbox-to-sandbox communication is unnecessary.

### E2B fixes attempted before retirement

- Increased the stream deadline from 25 to 60 seconds.
- Added per-request six-second child-process deadlines.
- Added staged progress receipts and A/B log visibility.
- Classified a request timeout as inconclusive rather than as proof of a blocked route.

These changes improved diagnosis but did not remove the underlying architecture friction.

### Architecture pivot

The user retired further E2B connection tests. The new design became:

```text
GPT-5.6-Sol Supervisor / Codex harness
                |
        local trusted broker
                |
       GLM Controller decision
                |
     one local Docker B Researcher
                |
       code + bounded experiments
                |
     independent local evaluator
```

B has no direct access to A, paid keys, budget, evaluator or host home.

Docker Desktop was initially installed but not operational:

- Desktop 4.37.2;
- backend socket returned `ECONNREFUSED`;
- bundled diagnose process crashed with `SIGSEGV`;
- daemon remained unavailable;
- existing Docker VM data was approximately 32 GB, so no reset or destructive reinstall was attempted.

The user started/upgraded Docker Desktop to 4.91.0 with Engine 29.8.0.

- read-only root;

The host broker was additionally hardened to reject guest-controlled symlink traversal using no-follow directory handles.

## 2026-09-18 — Data admission Gate 0 and construction of the live outer runner

### Data audit performed

A read-only audit reconstructed the current data and exposure boundary without opening sealed values.

Key findings:

- 2024 whole-season 60-second event-clock support: 67.64%.

- Only one Train game had a direct local opening receipt.

- No block of at least 20 dates was certified as untouched.

### What system problem was found

The data problem was not simply “too few rows.” It was a combination of:

- incomplete historical market identity and fill coverage;
- sparse short-horizon labels;
- uncertain historical access provenance;
- an insufficient number of distinct Final dates;
- missing evidence that unknown games were never opened.

Absence of a receipt was therefore not allowed to become proof of non-exposure.

### Data orchestration fix

The Supervisor created an eight-gate admission plan:

1. freeze current evidence and exposure;
2. bounded source research;
3. predeclared small source canaries;
4. full-season source inventory;
5. event-time joins and candidate labels;
6. truly independent Final period;
7. statistical sufficiency and strong baseline readiness;
8. exact release before experiment.

Gate 0 produced an immutable metadata inventory. A schedule-only prospective candidate of 20 future 2026 dates / 104 games was recorded, but not admitted.

### Controller→B engineering work

The offline fake-first-response adapter and fake-B broker flow passed. Exact source review then found several gaps.

#### Gap 1: source manifest omission

The new adapters were not included in the source-publication manifest. The manifest was updated and tests were added to reject future omissions.

#### Gap 2: fake-only modules

The existing modules explicitly accepted only `OfflineFakeBackend` and `OfflineFakeLocalB`. A published fake adapter could not be relabelled as a live Controller path.

#### Gap 3: task cardinality mismatch

The B guest hard-coded 20 orders. A one-task GLM canary would finish its one task and then wait for 19 more, preventing process-exit and cleanup evidence.

#### Gap 4: missing outer runner

No component atomically bound:

- exact release;
- global state;
- unique run ID;
- authoritative budget;
- provider call;
- child process and container;
- terminal receipt and cleanup.

#### Gap 5: independent fail-closed defects

An adversarial review found:

1. state could change during the process/container-clear callback, after the last check but before provider dispatch;
2. a failure receipt could be written before reservation cancellation and cycle close, so it described stale state.

### Fixes

- Added one-task B mode while preserving the existing order/ACK/event contract.
- Added a production-capable live adapter with strict fake tests.
- Added a reviewed outer runner.
- Rechecked state, budget, source, runtime and input immediately after the cleanup callback and before dispatch.
- On pre-dispatch failure, cancelled reservation and closed the cycle before writing the final failure receipt.
- Preserved cancellation/close errors separately without hiding the original failure.

### Effect

- Independent rereview found both fail-closed defects fixed.
- 110 exact release tests passed.
- Protocol v0.1.6 was published to the user fork after explicit authorization.
- No real model/container run or prediction result occurred during the release work.

### Next step at the time

Run one bounded live GLM → broker → one-task local-B canary under the published source, protected global state and authoritative budget.

- classifies an invalid response as `malformed_data`;
- preserves the failed ID and enters `repair_pending` instead of retrying.

Thirty combined Gate 1/watchdog tests passed. This was offline runner validation; no public request or model call occurred.

### Outer blocked-child monitor

An independent outer monitor was added so the system does not depend on a stuck child to report its own timeout.

It reads only:

- the active durable task;
- bounded worker-log tail hash;
- Supervisor-owned process/container/data/budget evidence.

For a stalled child, it first freezes an immutable incident. Only the exact recorded PID and labeled container are then eligible for cleanup. The monitor never automatically retries.

## What changed in the research hypothesis

At the beginning of the week, the working hypothesis emphasized memory policy: perhaps Archive memory makes the researcher better than Fresh.

After the full experiment, the stronger conclusion was different:

1. Archive may prevent forgetting, but the measured Archive-vs-Fresh advantage is too small and unstable to be the central result.
2. Compact memory can be actively harmful.
3. Ordinary trainer choice and one dominant state feature explain larger gains than memory format.
4. The dominant feature may not be available quickly enough in live use.
5. The current data and Final design are not strong enough to support a publishable recursive-improvement claim.
6. A functioning recursive system must improve not only models but also detect and repair data, runtime and orchestration bottlenecks without silently relaxing scientific rules.
