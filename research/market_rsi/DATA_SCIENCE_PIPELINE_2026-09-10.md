# 做模型之前，先把数据工作做完

Controller不能下载一份大文件就开始比较模型。它要先检查数据、解释问题、决定处理办法，
把结果交给runner核对。缺了证据就是“还没查清”，不是默认通过。

GLM仍决定来源、采样、特征、目标和模型。Harness负责工具、记录、因果时间、权限和
验收，不替它挑一个更好看的方案。这个顺序不改变原来的t7模型和目标，也不重写旧实验。

当前代码入口是[Data Scientist Harness](data_scientist_harness/README.md)：它作为Codex
工具层供GLM调用，每轮使用，不是另一个controller。文献、统计、训练、记录已形成可运行
的最小闭环。免费实际Codex canary05完成14次工具调用和四种CPU训练；不是GLM自主研究。
当前真实来源未通过，正式实验仍不能开始。具体未完成项和偶发错误见入口说明。

## 每做一个组件，先检查文献依据

数据质量、Feature engineering、Trainer engineering都按“实际问题 → 文献方法与限制
→ 适用性判断 → 小实验 → 实现与结果记录”来做。不能只在archive里放几个标题，然后
凭印象选方法。新问题、新方法要补查；复用已有研究时说明理由。不设固定论文数量。

当前开发助手已经联网查阅并记录[本次方法研究](LITERATURE_TO_HARNESS_2026-09-10.md)。
旧controller的一些“文献搜索”实际上只搜冻结摘要。新增工具已通过实际联网元数据搜索
和HTML阅读canary；尚未宣称GLM自主完成文献研究。开发规则已写入本目录AGENTS.md。

## 按三个方向组织工作

### 一、数据质量：记录有没有错

先查缺数据、时间错位、身份不匹配、重复记录、异常报价和断流。保留原件，每项问题都有
数量、来源、处理规则和处理后的覆盖记录。没有查清的不能冒充有效观测。

这一层通过只说明记录可以被解释，不说明数据有预测价值。

### 二、Feature engineering：给模型什么信息、怎么表示

不只是列一份特征名字。先在允许探索的Train上看每条原始序列和派生特征的统计表现：

- 有多少有效值、多少种取值，变化有多频繁，连续不动有多久。按日期、市场和字段类型
  分开看，区分真正静止、过期值、稀有事件和固定属性。
- 分布、量级、极端值是否稳定；变化是不是集中在少数日期或市场。大量相关行不算同等
  数量的独立信息。
- 序列前后依赖多强，有没有明显的时段差异、趋势或噪声。时间间隔不齐时，不能把
  “上一行”直接当成相同长度的时间滞后；也不能跨断流算连续不动的时长。
- 在固定目标下，特征本身和目标有没有关系；与已有特征是不是重复，在哪些日期或市场
  有信息。线性相关很小不等于没有非线性或交互信息，不能一项指标决定删掉。

看完再由controller提出处理方法。例如保留原值、增加变化量、使用历史窗口汇总、
过去数据拟合的归一化，或者把“是否发生”和“发生时的大小”分开表示。也可以提出其他
方法；不是预先规定只能选这几种。每个方法都要说明解决哪个已观察到的问题，并记录
处理前后的分布、覆盖、变化率和信息量。并非每条特征都必须变换，也不是越会动越好。

这一层要求诊断和处理规则完整，不要求每个特征先证明能赚钱。没有信号也是有效发现。
不得用未来是否有变化筛Dev/Test；不得用全时期统计量归一化；不得平滑后改称原始价格。

### 三、Trainer engineering：模型怎么学

在明确的数据、目标和特征上研究模型结构、训练算法、loss、权重、正则化、训练窗口和
超参数。方法库可以扩展，不把controller限制为某一种trainer。新方法先通过正确性、
时间隔离和费用检查，再参与比较；列在文档里不等于已经实现或测试过。

同一份特征交给不同trainer，是训练方法比较；固定trainer比较不同特征，是特征比较。
Controller也可以提交两层一起改的方案，但只能报告组合效果；要判断是哪一层起作用，
需要补单层变化的对照。已有数据质量/目标/切分改变时，也要单独声明，不能暗中一起换。

分别保存“特征本身的诊断”和“训练后的表现”。如果特征在多期有信息，但当前trainer
没学出来，先检查训练方式，不能直接说特征没有用。训练正确但表现不好也是结果，不是
理由去反复打开同一个Dev或删掉不利样本。

数据、目标和时间划分是三层共用的定义。Train探索范围先登记；目标及正式评分规则在看
Dev前确定。每轮记录改变的是哪一层，以及其他定义是否保持不变。

实现状态：已有目标活动率诊断、部分相关/冗余诊断与训练比较；新工具补了逐字段/逐日
统计、候选的逐市场日期统计，以及强制检查后的CPU训练入口。并非上面所有研究项目
都已自动实现，尚不含完整平稳性、有效样本量与特征家族诊断。没有打开新时期。

## 正式实验前的顺序

开始时只查来源、字段结构和时间覆盖。读价格、算目标或比较特征之前，必须先登记哪些
时期允许作为Train探索，哪些时期还封存。下面第7步是在目标窗口确定后核对最终切分和
隔离间隔，不是允许先看完所有时期的结果、再决定哪些算Train。

| 阶段 | Controller需要做什么 | 必须留下什么 |
|---|---|---|
| 1. 来源与原件 | 查来源说明，核对具体文件、版本、用途与空间 | 下载清单、原文件hash、来源说明；下载和备份分账 |
| 2. 覆盖与样本量 | 查实际日期、市场、缺口和采集心跳 | 逐日逐市场覆盖表；不能只报行数或GB |
| 3. 字段与异常 | 分清成交、盘口、midpoint、市场和token的含义 | 字段对照、异常行数量、每种异常的处理规则 |
| 4. 当时可见的数据 | 核对事件时间、接收时间、延迟、重连和跨表连接 | 只用当时已到达的数据；缺失与歧义保留为未知 |
| 5. 目标 | 在Train上检查目标变化、噪声、完整标签窗口和不变预测 | 目标定义、单位、基线误差、选择理由；看Dev前冻结 |
| 6. 特征 | 检查历史窗口、缺失、归一化、信息量和重复信息 | 相同目标下的Train诊断，按日期和市场拆分 |
| 7. 时间划分 | 分开Train、Dev、Test，检查整市场和标签跨界 | 固定清单、隔离间隔、已经看过哪些日期的记录 |
| 8. 实验前检查 | 跑小规模真实基线，核对评分、环境、成本和超时 | 可复查回执；之后才允许进入正式实验的下一层检查 |

先确定目标，再判断特征对这个目标有没有信息。目标变了，相关的特征检查必须重做。
Train内部的探索可以迭代；不要求第一次就选对。但不能看过Dev后悄悄改目标，继续把同一
个Dev当成新证据。数据诊断、小样本运行和工具canary也不能冒充正式结果。

## 之前发现的问题，具体怎么处理

| 问题 | 处理方式 | 不能做什么 |
|---|---|---|
| 文件很大，真实覆盖很短 | 根据实际时间和市场检查，补足数据或明确用途限制 | 把缺失日期补成“价格不变”；靠训练次数凑证据 |
| token和market对不上 | 查当时已存在的市场映射；查不清的在派生数据里标为无效 | 猜着改名，或者拿后来公布的映射解释过去 |
| 买价高于卖价等异常 | 保留原行、标原因；无效状态不能进入可用报价 | 改成正常报价，或回退到更早的正常报价掩盖错误 |
| ID重复 | 区分来源、文件和原始行；确认事件相同后才处理派生重复 | 按ID全局去重，误删不同事件 |
| 文件日期和实际时间不一致 | 从核实后的时间字段建时间轴，保留来源时区证据 | 统一猜一个时差，按文件名直接切Train/Dev |
| 断流、重连、报价过期 | 分开看行情、心跳和订阅；按已声明规则重建状态 | 认为`gaps`表为空就从未断流；无限沿用旧报价 |
| K线补录、最终值提前可见 | 核实实际可用时间；没查清的不能作为当时输入 | 在K线开始时使用最终收盘价。t7不用K线，不能把缺K线误列为它的输入问题 |
| 太多记录不变、目标太平 | 保留原始记录；Train上比较目标变化率、基线误差和采样办法 | 因为未来不涨不跌就删Dev/Test记录 |
| 特征有信息，模型却没学到 | 分开查特征信息和训练方法，保留失败与条件 | 只看一次模型分数就断言特征没用 |
| 反复看少数日期 | 记下已暴露日期，只当诊断；新结果使用事先隔离的时期 | 把旧检查集重新命名成新的测试集 |

104,836条身份不匹配、320条倒挂报价来自旧OpenMarket检查，不是新Vantage的检查结果。
Vantage目前明确查到的是覆盖不足。问题清单可以继承，某份数据的“通过”不能直接继承。

## “检查完成”不等于“模型应该提高”

特征可以没有信号，模型可以没有进步。流程要求的是测过、解释清楚、留下证据，不是每项
都必须得到正结果。20个完整日期也是当前要求的最低门槛，不是保证足够，更不是保证赚钱。

预测研究报告预测误差；需要讲交易赚钱时，再单独核对可执行价格、费用和交易规则。价格
误差换成bps必须写明单位，不能把概率价格的bps当成实际收益。

- 新的独立验证前置入口会先检查数据科学报告，再进入原有验证检查；不是替代原有预算、
  隔离和一次性测试要求，也没有改动旧的冻结入口。
- 32项检查与旧问题已经通过现有controller工具实际传递。28项相关测试通过。
- 真实Codex端到端canary通过：两条固定测试回复、四次实际工具调用，没有Tinker调用。

  独立核对了调用、第一份决定、188份源码和费用回执，没有训练或打开测试集。

还没完成：

- 把每一项来源专用检查都自动化，并把最终的新实验执行器接到新的前置入口。
  现在没有宣布所有旧入口都已受这个新检查保护。
- Controller处理新发现的方式还要加强。它这次仍提交同一来源的检查方案，但没有明确

  工具与费用审计通过，不等于这个研究答复已经处理好了新证据。

## 这次实际卡在哪里

Vantage在原方案的46天窗口里只有6天有记录，合计617个UTC分钟。它单独不能满足原先
至少20个完整日期的要求。5.99GB主档还没检查，不能说它也失败了，更不能把它默默删出方案。

下一步先修好新发现的传递：把当前已知事实与旧方案分开显示，要求controller逐项说明
新发现会改变什么、下一步需要补什么证据。它可以保留原来源，但不能把已经查完的问题
重新当成未知，也不能忽略失败继续训练。保留本次原始答复，不为得到满意答复反复重抽。

随后才继续缺失的数据检查，并接好正式执行入口。覆盖没补足之前，不靠删静止记录、
增加训练次数或降低验收条件来凑一个实验结果。
