# 9月13日：不是模型没提交，是接口把参数类型改了

Controller 三次提交单文件核验请求，接口三次报“需要文本”。实际的工具调用里，
它把 JSON 内容放在文本参数里；我们的解析器不看参数定义，直接尝试解析 JSON，
因此把文本改成了对象。模型第四次加上文字包裹后才绕过去。这三次错误不能简单归因于模型。

## 依据和修复

读取当前固定 GLM tokenizer 的原始模板（revision
`aca966e4e02791568aa6a4ced368624b3d897f42`），第152–157行明确：字符串原样输出，
非字符串才转为JSON。模板文件hash为
`3740abcea51c45830cb3ca562084ad5fb2ef53589376f73332e9886f93ade41c`。
这是2026-09-13读取本地固定上游模板的结果，不宣称新搜索或金融方法研究。

修复放在 `codex_glm_responses_adapter.py`，由 `codex_glm_provider.py` 传入本次请求
实际提供的工具参数定义：声明为文本的保留文本；对象、数组、整数仍按原方式解析。
没有替模型重写研究参数，也不自动补缺字段或调用不存在的工具。
旧模板、旧回复、旧失败和旧版本都不改。另升 `dsh-v1.4.1`，属于人工接口修复。

已发布到用户私有origin，commit `d9e3e5ac90adbc744e69fee81c5de823d5afe305`。
远端tag和全部运行源码已核对；发布回执为
`artifacts/releases/dsh-v1.4.1/release.json`，内部hash
`00b7b4b6ec11aa37b88886378580b83c01483b5b6f531a526701e110d78fbcd5`。
没有借发布动作启动新的付费会话。

另一个办法是改提示词，要求每次多加一层引号或文字。但这样让模型适应解析错误，
而且合法的JSON文本、数字文本仍可能出错，因此采用按参数定义解析。
